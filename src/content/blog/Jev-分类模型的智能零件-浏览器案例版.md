Jev 发布那天，创始人 Diogo Almeida 发了一条很反常识的 X。

[![Diogo Almeida 发布 Jev 时的 X 原帖截图，含发布视频与浏览量](images/jev-launch-x-post.png)](https://x.com/CompleteSkeptic/status/2099925682726002904)

*Diogo Almeida 发布 Jev 时的 X 原帖截图。点击可查看原帖。*

他参与过让 ChatGPT 更会听指令、更会和人对话的研究。但他说，过去几年一直想不通一件事。

为什么已经这么聪明的聊天模型，还没有带来我们以为会出现的大规模自动化？

他的答案不是再做一个更会聊天的大模型。

而是，干脆让模型别聊天了。

这就是最近两天突然很火的 Jev。

先别急着看 System One、RLCD、并行采样、快 200 倍这些词。要是只想先弄明白 Jev 是什么，有一个足够直白的答案。

> Jev 本质上是一个为软件设计的分类模型。

你把当前情况和几个候选答案交给它，它不写一段话，只会告诉程序该选哪个、各选项的可能性多大，以及这次选择有多确定。

就这么简单。

先看一个不需要任何技术背景的例子，Mario。

画面里角色在跑、跳、躲障碍。把这件事拆开看，游戏代码维护地图、碰撞、动画和按键执行；Jev 每一轮只根据当前局面，在当下允许的动作里选一个。

所以 Jev 不是游戏引擎，也不是直接接管每一帧的物理和控制。它更像拿手柄的玩家：决定下一步按什么，游戏本身负责让这一步真正发生。

这个 demo 能帮我们建立直觉，但不该被读成「Jev 是一个专门玩 Mario 的模型」。换一套程序状态和候选动作，同一个位置也可以用在客服分流、网页操作或模型路由里。

客服收到一句，订单过了七天还没到，能不能退款？

Jev 不负责替客服写一段安抚话术。系统把当前对话、订单状态和允许走的路径交给它。

```text
当前情况，订单超期，物流仍在运输中，用户要求退款

候选路径，查询物流 / 发起退款 / 请求补充信息 / 转人工
```

它返回的会是这样的东西。

```text
选择，查询物流
各选项概率，查询物流 0.91，发起退款 0.04，其他 0.05
置信度，0.87
```

然后，程序再按自己的规则决定要不要调物流接口，要不要转人工。

它不制定退款政策。

也不拥有退款权限。

它只是在几条已经存在的路里，帮系统选一条。

这就是 Jev。

## 它和垃圾邮件分类器有什么不一样

说到分类模型，很多人可能会想，垃圾邮件分类、图片识猫狗、商品标签识别，这些不早就有了吗？

没错，分类本身一点都不新。

传统分类器最适合的场景，是任务稳定、标签稳定、数据也足够稳定。比如邮件是垃圾邮件还是正常邮件，商品是不是违禁品。你有一大批历史样本，能训练一个很便宜、很专门的模型，甚至简单到写几条规则就够了。

Jev 想解决的不是这类题。

它面对的是另一种麻烦。

输入依然是自然语言或程序状态，但候选项会跟着当前任务变化。今天是「查物流、退款、转人工」，明天可能是「搜索、读文件、运行测试」，后天又变成当前网页上编号 1 到 40 的按钮和链接。

你不可能为了每一个新页面、每一个新 Agent、每一套临时流程，都重新收集数据、训练一个分类器。

这时就需要一个能读懂通用语义、又愿意老老实实在候选集合里作答的模型。

TypeSafe 把它做成三种基本问题。[官方文档](https://docs.typesafe.ai/introduction)

| 你要问的事 | Jev 返回什么 |
| --- | --- |
| 该选哪个 | 一个候选项、各候选项概率、置信度 |
| 这件事处于哪个等级 | 分数、各等级概率、置信度 |
| 这句话是否为真 | 是的概率，0 到 1 |

Choice、Score、Noul 这三个名字可以以后再记。

先记住一个边界就行。

Jev 不擅长生成答案。

它擅长在你允许的答案里做判断。

## 看一段视频，就知道它在 Agent 里干了什么

前面的 Mario 展示了 Jev 如何在一组动作里选下一步。网页场景的关键变化是：候选动作和目标会跟着页面不断变化。

我们再看一个更日常的场景，订机票。

Browser Use 做了一个开源的浏览器 Agent。目标很普通，从苏黎世找一张去伦敦的单程机票。视频里真正值得看的，不是它七秒多就找到了机票，而是它每一步怎么分工。

*Browser Use 的 Jev Ultrafast 浏览器 Agent 演示。Jev 在当前页面已编号的控件中选择操作和目标，只有需要填写文字时才调用小模型生成输入。视频与代码来自 [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast)，按 [MIT License](https://github.com/browser-use/jev-ultrafast/blob/main/LICENSE) 使用。*

网页打开后，系统先把页面整理成一张元素表。

```text
[1] 按钮，往返
[2] 下拉框，出发地，旧金山
[3] 下拉框，目的地，空
[4] 输入框，出发日期，空
...
```

然后 Jev 要回答的，不是「请分析一下这个页面」。

而是两个更小的问题。

```text
下一步是什么操作，点击 / 选择 / 滚动 / 等待 / 输入 / 完成？

如果要操作，目标是哪个已编号元素？
```

例如，它选「点击第 3 个元素」，浏览器就去点击目的地下拉框。它选「等待」，浏览器就等待新状态。只有当操作是输入文字时，系统才叫另一个小模型写出 Zurich 或 London 这样的文本。

整个循环是这样的。

```text
网页当前状态
        ↓
页面元素被编号，形成有限候选
        ↓
Jev 选择操作和目标
        ↓
浏览器执行，页面产生新状态
        ↓
下一轮再问 Jev
```

这比抽象解释更容易看明白。

Jev 不是浏览器。

不是网页爬虫。

也不是负责填写所有文字的大模型。

它只是浏览器 Agent 里那个不停决定「下一步该干什么」的分类器。

腾讯技术工程做过一个网页小游戏，也用了同样的结构。游戏代码维护地图、伤害和碰撞，Jev 只在上、下、左、右、攻击、喝药这些合法动作里选择一个。用一句很形象的话说，Jev 是拿手柄的玩家，代码才是游戏本身。[腾讯技术工程的实测](https://mp.weixin.qq.com/s/w4kDVSF_beVA7CVhL_Xohw)

浏览器和游戏看起来隔得很远。

底下其实是一回事。

系统维护世界，Jev 在当前世界里选下一步。

## 为什么大模型已经会输出 JSON，还要做 Jev

这才是更值得问的问题。

GPT、Claude、Gemini 都能按 JSON Schema 输出结果。让它们从几个工具里挑一个，也不难。不能把「不会乱输出不存在的字段」当成 Jev 独有的能力。

区别要放到调用频率里看。

如果只是偶尔分一条客服工单，多花几百毫秒，可能谁也感觉不到。

可一个浏览器 Agent 要连续决定点哪个按钮、滚哪一屏、选哪个下拉项。一个复杂 Agent 每完成一次任务，可能要做几十次工具选择。一个内容平台每天可能要处理百万次审核和分流。

这时，选择下一步的次数往往远多于真正需要写文字的次数。

Browser Use 的这次航班搜索，是 17 次 Jev 请求、2 次文字生成调用。它只是一个具体任务的记录，不能推广成所有网页任务都如此。但这 17 比 2 很形象。

很多 Agent 的时间，不是花在写，而是花在不停地决定下一步。

Jev 的赌注就在这里。

把这些高频、有限选项的判断，从通用大模型的文本生成过程中拆出来。TypeSafe 宣称它因此可以在 70 到 500 毫秒内完成一次调用，输入价格为每百万 token 0.042 美元，输出不单独计费。[TypeSafe 的发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

这些性能数字仍然只能算厂商主张。输入长度、网络、负载、候选数和比较对象都会影响结果。Browser Use 自己也把这段航班视频的边界写得很清楚，它是同一浏览器配置下同一任务的少量重复，不是通用可靠性基准。[测量说明](https://github.com/browser-use/jev-ultrafast/blob/main/docs/performance.md)

但方向是容易理解的。

当软件只需要一个选择，却每次都请一个擅长写文章的人来完成，多少有点像让律师替你按电梯。

大模型不是做不到。

只是它不一定是最合适的那个零件。

## 一个概率，不是一次授权

Jev 还有一个卖点，常被一句「它会给置信度」轻轻带过去。

但这件事比速度更重要。

假设它在一个游戏里选了攻击。

攻击的概率是 95%，置信度是 93%。腾讯的实测专门指出，这两个数不是同一回事，也都不是「这局有 93% 的概率会赢」。

一个数告诉你，攻击相对其他候选动作有多占优。

另一个数告诉你，这次选择的分布有多明确。

你可以想成考试。

有时你看四个选项，觉得 A 八成对。有时 A 和 B 都很像，你勉强涂了 A。最后答题卡上都是 A，但后者显然更应该被拦下来，再看一眼题。

Jev 给系统的价值，不只是一个 A。

还包括「我到底有多犹豫」。

不过，模型给出 0.9，不会自动等于它在你的业务里有 90% 正确率。概率是否校准，必须拿自己的历史样本验证。过去一千次置信度超过 0.9 的自动选择，最后到底有多少次真的做对了？不同业务、不同候选集合，答案都可能完全不同。

所以成熟的系统不能这样接。

```text
Jev 选了，立刻执行
```

而应该这样接。

```text
Jev 给出选择、概率和置信度
        ↓
代码检查金额、权限、预算、地域、库存等硬规则
        ↓
高置信度走自动路径，模糊情况升级给 LLM 或人工
        ↓
记录真实结果，持续检查这些置信度到底靠不靠谱
```

调用 API 很简单。

把它接成一个值得信任的系统，难得多。

## 它会出现在哪里

现在再看最近那些看上去很散的 demo，浏览器操作、工具选择、模型路由、内容审核、交易动作，就接上了。

它们做的都是同一件事。

把大任务里反复出现的小判断单独拿出来。

浏览器 Agent 要选的是下一步点什么。

模型路由要选的是这个任务该送给快模型、强模型，还是普通代码。

客服系统要选的是工单进哪个队列。

内容审核要选的是放行、拦截，还是转人工。

千人千面的页面要选的则是，在已经批准的一组组件中，眼前这个 session 更适合哪一个。

这里的千人千面，不是 AI 现场给每个人生成一个全新网站。产品团队先定义组件和边界，A/B 测试先确定哪些组件值得保留，业务规则先划出不能跨越的红线。Jev 只根据调用方提供的 session 状态，在允许的候选里选择。

它不自动理解用户的人生。

它只回答系统此刻问它的那一道题。

## 它夹在规则、分类器和大模型之间

到这里，Jev 的位置就比较清楚了。

它不是所有分类问题的答案，更不是所有 Agent 的标配。

如果判断很简单，规则稳定，普通代码就够了。库存小于 3 显示「库存紧张」，订单金额超过某个数必须人工审核，这些没必要请模型参与。

如果标签长期固定，数据又足够多，传统分类器或专用小模型通常更便宜、更容易部署。垃圾邮件识别、违禁商品识别，都有很多成熟方案。

如果任务是开放的，需要理解含混目标、发散方案、写复杂参数、处理从没见过的新情况，大语言模型仍然更合适。

Jev 想占的位置在中间。

任务需要通用语义理解，候选和判断标准又会随当前页面、流程和会话变化。你不想为每个小判断训练一个模型，也不想让最贵的大模型在每个十字路口停下来写一篇小作文。

```text
稳定且确定，规则或普通代码
稳定标签且数据充足，专用分类器或小模型
开放、复杂、需要生成，大语言模型
候选动态、判断高频、需要语义理解，Jev 这类决策模型
```

这四格不是严格边界，更像一张选型地图。

Jev 真正的挑战，也来自它的两边。

上面是大模型厂商。结构化输出、工具调用、低延迟模型、蒸馏都在变强。只要大厂在关键场景里做到够快、够便宜，很多开发者不会愿意为了一个判断步骤多接一家供应商。

下面是规则和专用模型。任务一旦稳定下来，它们可能比远程 API 更便宜、更可控。

所以 Jev 能否成功，不是单次调用有多便宜，而是它能否在这片中间地带持续做到好用、稳定、容易接入。

## 智能开始离开聊天框

过去几年，我们很容易把 AI 想成一个聊天窗口。

你问，它答。你让它写，它写。你让它干活，它先说一大段，再去调工具。

Jev 看起来是在反着来。

它不想成为一个更会聊天的存在，它想成为软件内部一个安静的判断节点。用户不会知道它的名字，也不会看见它输出了什么。它只是在某个 Agent 要行动的时刻，帮它少走一步弯路。在某个用户犹豫的时刻，帮系统从已经允许的选项里选出一个更合适的下一步。

Jev 9 月 15 日才公开发布，仍处于 early access。它能否真的在生产业务里稳定胜出，现在谁也不能替市场下结论。官方的速度、成本和工作流效果值得继续看，真实业务里的复现和失败案例更值得等。

但它至少提出了一个值得认真讨论的问题。

我们是不是一直把大模型用得太粗了？

明明有很多地方不需要生成一篇内容，只需要一个受约束、能表达不确定性的选择，我们却总让最通用的模型包办一切。

如果以后智能真的会进入更多软件，它未必总是以聊天框的样子出现。

它会更像一个小小的分类模型。

藏在每一个需要判断的岔路口。
